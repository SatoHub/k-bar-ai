# 競馬AI予想アプリ「K-Bar AI」開発記 ― 個人開発でMLプロダクトを本番運用するまで

**執筆日:** 2026-07-11
**対象読者:** 個人開発・ML・Webアプリに興味のあるエンジニア／このプロジェクトの経緯を追いたい人
**ひとことで言うと:** 「競馬データをスクレイピング → LightGBMで予想 → Webで可視化 → VPSで自動運用」する個人MLプロダクトを、約4ヶ月半かけてゼロから本番稼働・一般公開まで持っていった記録。

---

## 0. この記事の狙い

このアプリ「K-Bar AI」は、競馬の出馬表・オッズ・結果データを自動収集し、機械学習で各馬の好走確率を予想し、SHAPで「なぜその馬を推すのか」を日本語で説明し、さらに予算に応じた買い目まで提案するWebアプリです。

単なる「動くものを作った」話ではなく、**個人開発で「データ収集の自動化」「MLの精度の壁」「自宅PCと本番VPSの環境差」「サイレントに壊れるデプロイ」といった現実の壁にどう向き合ったか**を時系列でまとめます。技術選定の理由と、失敗・方針転換も含めて残します。

---

## 1. プロジェクトの出発点

- **目的:** まず個人利用、将来は外部公開できる競馬AI予想アプリ。
- **本質的な要件:** `データ収集 → ML予想 → Web可視化 → 個人運用 → 将来公開`。この性格がほぼ全ての技術選定を決めた。
- **データ取得方針:** netkeiba / Yahoo! を Playwright でスクレイピング（間隔3〜10秒ランダムで相手サーバーに配慮）。JRA-VAN（公式データ）は実運用が軌道に乗ってから後追いで導入する段階戦略。
- **開発スタイル:** コストを最小限にしたい。方針書に沿った段階的開発。セッションをまたぐ継続性を重視し、`docs/progress.md` に毎回の到達点を残す運用。

---

## 2. 技術選定 ― なぜこの構成か

MLを中核に据えつつ、個人で低コストに運用でき、将来の公開にも耐える構成を選びました。

| レイヤ | 採用技術 | 選定理由（要約） |
|--------|----------|------------------|
| 言語 | **Python** | LightGBM/scikit-learn/SHAP/pandas/Playwright が全てPythonエコシステム。予想・API・スクレイパーを1言語で書けばロジックを共有できる。 |
| Web API | **FastAPI** | Python製でMLモデル(.joblib)を同一プロセスで直接読める。async対応で外部I/O待ち（ライブオッズ取得）に強い。Pydantic＋OpenAPIでフロントとの契約が明確。 |
| DB | **PostgreSQL 16** | 競馬データは関係が複雑で大量（学習データ161万件規模）。ウィンドウ関数で「過去5走の馬柱」を1クエリ、postgres_fdwで別DB横断参照など固有の強みを活用。 |
| ORM | **SQLAlchemy(async) + Alembic** | 型安全なORM＋マイグレーション自動化。VPS起動時に `alembic upgrade head` で新テーブルを安全に本番反映。 |
| ML | **LightGBM** | 表形式データでディープラーニングに勝る定番。高速・省メモリで個人PC/VPSで回せる。欠損値をそのまま扱える（競馬データは欠損多い）。 |
| 説明性 | **SHAP** | 「なぜこの馬か」を定量化し日本語ラベルで提示。ブラックボックスは信用されない＝説明が商品価値。 |
| スクレイピング | **Playwright** | オッズ・馬場情報（含水率・クッション値）はJSで後から注入される動的ページ。静的curlでは空になるため実ブラウザが必須。 |
| フロント | **Next.js 15 + React 19** | インタラクティブなUIが多い。将来公開時のSSR/SEO/最適化が標準装備。 |
| CSS | **Tailwind CSS 4** | 画面数が多い（シミュレーター・ヘッジ等）ので、CSS設計に悩まず高速にUIを組む。 |
| 基盤 | **Docker / docker-compose** | 自宅Windows PC ⇄ 本番VPS(Linux) の環境差をゼロにする。`libgomp1`依存などLinux固有の罠もDockerfileに封じ込め、GitHub Actionsから自動デプロイ。 |

> 詳細な選定理由は `docs/20260627-tech-selection-rationale.md` に別途保存。

## 3. 開発の流れ（時系列）

### フェーズ1 ― 基盤の三段構築（Step 1〜3）

最初に「データ→予測→表示」の縦串を通しました。

- **Step 1: データパイプライン + API**
  CSV取り込みパイプライン、FastAPI REST API（7エンドポイント）、PostgreSQL 16 + SQLAlchemy 2.0 async の土台。
- **Step 2: ML予測パイプライン**
  LightGBM予測モデル、SHAP説明、モデルバージョン管理、予測ログ保存。17テスト通過。
- **Step 3: フロントエンド**
  Next.js 15 + React 19 + Tailwind CSS 4。ダッシュボード／レース一覧／レース詳細＋AI予測（SHAP説明・信頼度バッジ・枠番カラー）／モデル管理。ダークモードUI（Noto Sans JP、グラスモーフィズム）。APIプロキシでCORS回避。

この時点で「手元のCSVを食わせれば予想が出て、Webで見られる」状態になりました。

### フェーズ2 ― データ収集の自動化（Step A）とUX拡張（Step B）

静的なCSVから、**自分でデータを取ってくる**アプリへ。

- **Step A: netkeibaスクレイピング**
  Playwright + BeautifulSoup4。パーサー（race_list / shutuba / odds / result）、`BaseScraper`（Playwright管理・レート制限3〜10秒・リトライ3回）、upsertパターンでDB保存＋ScrapeLog記録。CLIコマンド `scrape shutuba/odds/result --date` を追加。
- **Step B: フロント大幅拡張（13機能＋馬画像）**
  レース探索UX（カレンダー・月移動・馬場バッジ）、馬詳細ページ（馬画像・成績サマリー・馬場別成績バー）、リアルタイムオッズ（純SVG折れ線グラフ・枠色）、AI分析強化（SHAP横棒グラフ・荒れ度バッジ・コース適性★表示）、馬券シミュレーター＋収支管理、LINE通知スタブ。

### フェーズ3 ― 本番デプロイと運用自動化

「作った」から「動き続ける」へ。ここが個人開発で一番泥臭いところでした。

- **VPSデプロイ:** Docker Composeで本番構成（`docker-compose.prod.yml`）。Nginx + Basic認証で保護。
- **スケジューラ（APScheduler）による無人運用:** カレンダー(6:00)／出馬表(18:00)／AI予想(18:30)／オッズ(8:00-16:30の30分毎)／結果(17:00,19:00)を自動実行。ダッシュボードから手動トリガー・一時停止も可能。
- **LINE通知:** 予想・結果に加え、週次レポート・ハズレまとめ・月次改善提案まで拡張。
- **自動デプロイ:** master push → GitHub Actions `deploy.yml` → VPSで `git pull` + `build --no-cache` + `up -d`。
- **本番ヘルスチェック:** Playwright E2Eで本番VPSのデータ・UI状態を毎セッション自動検証する仕組みを整備。

この時期の修正コミットの多くは、**本番でしか起きない問題**との戦いでした。
- `libgomp1` 不足でLightGBMが本番で動かない → Dockerfileに追加。
- 出走取消馬の「ゴーストエントリ」自動クリーンアップ（BUG-002）。
- スクレイパーのブラウザクラッシュ時の自動再起動、メモリ節約のワーカー制限。
- AI予想データの重複防止（ユニーク制約＋UPSERT）。
- スマホ表示の横オーバーフロー修正（SP対応の連続改善）。

### フェーズ4 ― 馬券まわりの作り込み

「予想を見る」から「実際にどう買うか」を支援するフェーズ。

- **馬券シミュレーター:** 7券種（単勝〜三連単）対応。さらにボックス／フォーメーション／流し買いに対応。計算エンジン `betCalculations.ts` は組合せの純粋関数（C(n,k)・P(n,k)・流しの全パターン）で、JRA即PATの流し（軸1頭/2頭・着固定・マルチ）をJRA公式12ケースで検証。
- **オッズ全券種対応:** 全8券種のオッズ表示＋全買い方の組数・各組オッズ比較UI。
- **組合せオッズの落とし穴（`b437984`）:** netkeibaの組合せキーは区切りなし連結（例 三連単`141516`）なのに、フロント・バックエンドが `-` 区切りで参照していて**複数馬券のオッズが全て「—」**になっていた。3箇所を `join("")` に統一して解消。
- **収支の自動精算（`d38d601`）:** それまで「当たっても回収率0%」表示だった。原因は作成時に `is_hit`/`actual_payout` 未設定で自動精算が無かったこと。`settle_bets()` を新設し、結果が出た未判定馬券を全8券種で自動当落判定。TOP画面を開くだけで反映されるように。

### フェーズ5 ― JRA-VAN（公式データ）連携

netkeibaに加え、公式の確定データ・過去データ・血統を取り込むフェーズ。ここは設計が独特です。

- **環境の制約:** JRA-VANのJV-Linkは**32bit Windows専用**。自宅PCに専用環境（`.venv32` + pywin32）を構築し、`kbar_jravan` という専用DBに取り込み。
- **ID突合（決定的マッピング）:** 確率マッチ不要で、`race_id = 年‖JyoCD‖回次‖日次‖R` と `kettonum(血統登録番号) = horses.netkeiba_id` が完全一致（レース72/72・馬1027/1027）。
- **本番反映パターンの確立:** FDW（postgres_fdw）は自宅PC専用なので、本番VPSには出せない。そこで「**JV-Data由来データを自己完結テーブル化 → pg_dump(data-only) → scp → VPSでtruncate+restore（冪等）**」という同期方式を確立。
- **これで本番表示できるようになったもの:** 過去5走の馬柱、血統（父/母父）、確定オッズ・払戻、そして馬場状態（含水率・クッション値）。
- **馬場状態だけ設計が別:** 含水率・クッション値はJV-Dataに無く、JRA公式ページのJS注入値。**VPSが自身でJRA公式を直接Playwrightスクレイプ**する方式（自宅PC同期不要・過去遡及不可なので開催日に自動蓄積）。

### フェーズ6 ― 「市場を1つ抜く」挑戦とモデル精度の壁

このプロジェクトで一番の学びがここです。

**結論から言うと、モデルの精度向上は構造的に頭打ちだと厳密検証で確定しました。**

- 学習データはローカルに161万件（1986-2021）揃っており、データ量の問題ではない。
- ベースライン v1.0.0（target=is_place）: AUC 0.8115 / 単勝的中32.3% / 複勝的中52.5%。
- 相対特徴量の追加も、LambdaRank化も、回収率志向の「妙味モデル」も、**5585レースの厳密検証で改善ゼロ**。
- 理由: 現行モデルは実質**市場（オッズ/人気）のランキングを再現しているだけ**で、同じ情報からは市場を超えられない。控除率20%の壁に、同情報のモデルは勝てない。

**では諦めたのか？** いいえ、方向を変えました。「市場と同じ土俵で勝つ」のではなく「**市場が間違える瞬間を検知する**」方向へ。

- **荒れ度スコア（有効）:** 「そのレースが荒れるか」の予測は既存データだけで AUC 0.654、校正も単調（D1実18%→D10実58%）。最強因子は「本モデルの最高スコアが低い＝全頭low confidenceなほど荒れる」。→ 予想画面に製品化。
- **巻き返し穴（sleeper）検出:** 「前走別馬場で大敗→今走の馬場では実績→人気急落」という条件替わりの実力馬を、netkeiba全成績から自動炙り出し。
- **予算指定の買い目自動提案:** 予算を入れると券種・買い目・配分・想定的中率/払戻を自動提案。荒れ度でAIが狙いを自動切替。Harville基盤＋ガミ防止配分（当たれば必ず投資以上を保証）。
- **荒れ対応ヘッジ:** 「人気決着」と「荒れ」を相互カバーする2本立て（本命三連複／穴ワイド系）を自動生成。

> オッズ非依存の「ヒモ妙味」で市場を抜く試みは**無効**と判明（複勝市場は効率的）。妙味の再挑戦は脚質・展開・オッズ変動といった「市場がまだ織り込めていない新情報」の取得（レバーA）が前提、という整理に到達。

### フェーズ7 ― 公開・ポートフォリオ化

- **GitHubリポジトリを公開(public)化。** 公開前にハードコードされていた認証情報・IP・SSHキーを全て環境変数化し、機密は `.env`/`.env.local` 管理（コミット厳禁）に統一。
- READMEをポートフォリオ向けに強化し、閲覧限定LICENSEを追加。

## 4. 途中で踏んだ地雷と得た教訓

個人開発で「本当に効いた」学びを厳選して残します。

### 教訓1 ― デプロイは「失敗をサイレントに握り潰す」のが一番怖い
本番が数ヶ月間、あるコミットで固着していた事件があった。原因は、VPSのgit remoteに埋め込んだ**PATが失効**して `git pull` が失敗していたのに、`deploy.yml` がそれを成功扱いにしていたこと。
- **対策:** ①認証をSSHデプロイキーに恒久切替。②`deploy.yml` を `set -euo pipefail` + `git pull --ff-only` + **pull後のHEADが `github.sha` と一致するか検証（不一致なら `exit 1`）** で堅牢化。「失敗を確実に検知して止める」ことがCI/CDの本質だと痛感した。

### 教訓2 ― キー・区切り文字の不整合は「静かに全滅」する
組合せオッズが全て「—」になっていたバグは、フロントとバックエンドで組合せキーの区切り文字（`-` vs 連結）が食い違っていたのが原因。**外部データのキー形式は実物を確認して1箇所に統一**する。

### 教訓3 ― MLの精度は「損失関数」より「情報量」で決まる
LambdaRankに変えても相対特徴量を足しても1ミリも改善しなかった経験から、「モデルを凝る前に、そのデータに市場を超える情報が入っているかを疑う」を学んだ。**市場（オッズ）と同じ情報しか持たないモデルは市場に勝てない。**

### 教訓4 ― 環境差はDockerで潰し、越境データは「自己完結テーブル＋pg_dump同期」で運ぶ
自宅32bit Windows（JRA-VAN）と本番Linux VPSという厳しい環境差を、Docker（構成の再現）と「FDWに依存せず実テーブル化して同期」という2段構えで解決した。**"開発環境でしか動かないデータ源"を本番に届ける設計**は個人開発でも避けて通れない。

### 教訓5 ― 公開前のシークレット棚卸しは必ずやる
public化の前に、コード内の認証情報・IP・SSHキーを全て環境変数へ追い出した。git履歴に旧値は残るが、**旧値は事前に無効化（ローテーション）**しておけば無害化できる。

## 6. 機能一覧（現時点）

- **AI予想:** LightGBMで好走確率を算出、SHAPで日本語の予想根拠を提示、信頼度バッジ・コース適性表示。
- **荒れ度スコア:** そのレースが荒れる確率を提示（校正済み）。
- **巻き返し穴（sleeper）検出:** 条件替わりの実力馬を全成績から自動抽出。
- **予算指定の買い目自動提案:** 券種・買い目・配分・想定的中率まで自動生成（ガミ防止モードあり）。
- **荒れ対応ヘッジ:** 人気決着と荒れを相互カバーする2本立てを自動生成。
- **馬券シミュレーター:** 7券種＋ボックス/フォーメーション/流し、全組オッズ自動取得、買い目別の掛け金配分。
- **収支管理:** 馬券記録の当落・払戻を自動精算、回収率・的中率を可視化。
- **オッズ:** 全8券種・全買い方の組数/オッズ比較。
- **公式データ:** 過去5走の馬柱、血統（父/母父）、確定オッズ・払戻、馬場状態（含水率・クッション値）。
- **無人運用:** スケジューラによる自動収集、LINE通知、本番ヘルスチェック。

## 7. これからやりたいこと

- **控除率超えの厳密決着（Benter方式）:** オッズ非依存の実力確率 `P_fund` と市場確率 `P_market` をメタモデル（ロジスティック回帰）で合成し、ケリー基準で配分して月別ROIをバックテスト。「公開データに本当にedgeがあるか」を素朴なEVではなく正しい手法で決着させる。
- **レバーA（新情報の取得）:** スクレイパーを脚質（コーナー通過順）・オッズ時系列に対応させ、現在レースでもこれらを特徴量化する。過去データは揃っているが直近スクレイプが0%なのが課題。
- **運用ウォッチ:** 月次でAI回収率・的中率を追い、条件別の偏り（妙味の芽）を観察する。

## 8. まとめ

K-Bar AIの開発は、「モデルを賢くすれば勝てる」という素朴な期待からスタートし、**厳密な検証を通じて「同じ情報では市場に勝てない」という壁に正面からぶつかり、そこから"市場が間違える瞬間を捉える"方向へ舵を切る**、という知的に面白い旅でした。

技術的には、MLを中核に据えたPython/FastAPI/LightGBM/SHAPの構成、自宅⇄VPSの環境差をDockerと自己完結テーブル同期で潰す設計、サイレント故障を許さないCI/CDの堅牢化――個人開発でも「本番を止めずに動かし続ける」ためのエンジニアリングが詰まっています。

派手な精度自慢ではなく、**現実のデータと市場の効率性に誠実に向き合った記録**として、この開発記を残します。
