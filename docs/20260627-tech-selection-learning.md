### 追加でカバーした周辺基礎トピック（Step2の流れで）
- **ポート**: コンピュータの「ドア番号」。IP(住所)1つでもポートで繋ぐ先のアプリを区別。80=HTTP/443=HTTPS(ブラウザが自動で叩くWeb玄関)。
  本番は nginx だけが80/443を外に開き、backend(8000)/frontend(3000)は内部用でnginx経由のみ。
- **Dockerの具体構成**(現物確認): docker/ に compose 2種 + Dockerfile.backend(python:3.12-slim,libgomp1,playwright) +
  Dockerfile.frontend(node:22-alpine,2段階ビルド) + nginx/nginx.conf。コンテナ同士はサービス名で通信(POSTGRES_HOST: postgres)。
  ボリューム(pgdata)でDBデータ永続化。depends_onで起動順制御。
- **なぜ箱に分けるか**(ユーザーのつまずき所→解決): 4つは必要物が全然違う別ソフト(backend=Python/frontend=Node.js)。
  1箱に全部詰めると重い・1つ直すと全部再ビルド・1つ落ちると全部停止・バージョン衝突。1ソフト=1箱なら独立更新/再起動/版管理でき、公式完成品(postgres/nginx)もそのまま置ける。
- **複数サーバーの関係**: 4つはソフトとしては別サーバーだが1台のVPS内に同居。司令塔はなく ユーザー→nginx→backend→postgres と隣へ依頼を渡す連鎖。
  同じプログラムが相手によりサーバー役/クライアント役に変わる(相対的)。
- **GitHub Actions**: 設定場所=`.github/workflows/deploy.yml`。masterへのpushが引き金→GitHubの作業マシン(ubuntu-latest)が起動→
  SSHでVPSにログイン→git pull(git) → docker build/up(Docker)を自動実行。pull後HEAD検証など失敗検知の安全装置入り。
- **SSH**: 遠くのVPSに遠隔ログインしてコマンドを打つ仕組み。鍵(.pem/secrets.VPS_SSH_KEY)で本人確認。
  ⚠️「GitHubログイン」と「VPSへのSSH」は別の鍵・別のドア。pushはGitHub認証、SSHはVPS専用鍵。繋がりは"VPSの鍵をGitHub secretsに預けてある"こと。
  「本番はVPS内で動く→更新にはVPS上の操作が必要→その手段がSSH」はユーザー正答。
- **git pull/build/up**: pull=git、build/up=Docker。順番=①最新コード取得→②イメージ作り直し→③コンテナ起動。
- **Ubuntu**: Linux(OSの系統)の中で最も人気のディストリビューションの1つ。OS=Windows/macOS/Linux。コンテナの中身もよくLinux(Alpine等)。
- **インフラ学習の位置づけ**(メタ): 概念理解はインフラ必須。段階=①概念(今ここ)→②書ける→③運用→④設計。個人運用は①〜③で十分。ユーザーは既に実地でインフラを触っている。

### Step2で解いた誤解（重要・再開時に踏まえる）
- 「Dockerは環境統一だけのもの」→ 主目的は正しいが片面。コンテナは「動くアプリ本体」でもある。
- コンテナにアクセスが殺到する＝中のアプリ(FastAPI)が処理する。処理能力に上限があり超えると行列＝遅延。
- 複数コンテナには2種: ①同じものを量産(負荷分散・今は不要) ②違う役割を分ける(アプリ/DB/pgAdmin・これを実使用)。
- 1端末で複数コンテナを同時に動かせる(1端末1コンテナではない)。
- 個人利用の今はアプリ1コンテナで十分。量産は将来の外部公開時の選択肢。
- 「Dockerはサーバー？」→ No。Dockerはサーバー(アプリ)を箱で動かす"管理人/土台"。サーバー本体はコンテナの中身。
- ★コンテナ構成は開発と本番で違う（現物確認済み）:
  - 開発(docker-compose.yml): **2コンテナ** = postgres + pgadmin。アプリ/フロントは直接起動(uvicorn/npm)＝開発が速い。
  - 本番(docker-compose.prod.yml): **4コンテナ** = nginx(門番/Basic認証/振り分け) + frontend(Next.js) + backend(FastAPI) + postgres。
  - 機能(役割)ごとに1コンテナ。mem_limitも役割別(backend1024m最重・nginx64m最軽)。
- 「AWS EC2はDockerのようなもの？」→ No。レイヤーが違う。EC2/VPS=借りるコンピュータ(場所)、Docker=その上で使う道具(箱)。
  EC2を借りる→Dockerをインストール→コンテナ起動、と重ねて使う。**ユーザーのVPSはEC2と同じ立ち位置**。
  EC2の中身=仮想マシン(重い・OS丸ごと)、Docker=コンテナ(軽い・環境だけ)。Dockerは業界標準だが全サービスが使う訳ではない。
- 本番のサーバーは全てDockerコンテナで起動(`up -d --build`一発、masterへのpushで自動)。開発はDBのみDocker・アプリは手動起動。
- 「サーバーって何？APIのこと？」(基礎・重要):
  - サーバーは2つの意味: ①ハード=コンピュータ(VPS/EC2) ②ソフト=リクエストに応答し続けるプログラム(FastAPI/PostgreSQL)。
  - APIはサーバーではない。API=「サーバーに何を頼めるか」のメニュー/約束事。関係は「サーバー(厨房)がAPI(メニュー)を提供」。
  - レストランの比喩: 建物=①ハードサーバー / 厨房+ウェイター=②ソフトサーバー / メニュー表=API / 注文=リクエスト / 料理=レスポンス。
- 「依頼の向き」(ユーザーが最初混同→訂正済み): 依頼(リクエスト)を出すのは**クライアント(フロントエンド/ブラウザ)**。
  APIは依頼を出す主体ではなく「依頼の出し方の決まり」。向き=クライアント→(APIに従い依頼)→サーバー→(応答)→クライアント。
- ★「API≠DB操作の主体」(ユーザー自力で正答): APIは「何ができるか」の決まりでDBには触らない。
  DBへの格納/取り出しを実際にやるのはサーバー(FastAPI)。Step1の「バックエンド→DB」がこれ。
  → サーバー/API/DB/クライアントの関係を完全理解。Step3以降に進める状態。

### 直近のやり取りで確定した重要点
- ⚠️ **開発環境はUbuntuではなく Windows 11**。本番VPSはLinux（ディストリは未確認＝SSHで確認可能）。
  → Dockerが吸収しているのは「Ubuntu同士のバージョン差」ではなく「Windows⇄Linuxという根本的なOSの違い」。
- `deploy.yml`の`ubuntu-latest`はGitHub Actionsの作業マシンであり、VPSのOSではない。
- Dockerが固定するのは「ホストOS」ではなく「箱(コンテナ)の中身＝Linux+Python+ライブラリ」。
- Dockerを検討すべき判断基準: 複数人開発／本番がレンタル(VPS)／開発と本番のOSが違う／依存が複雑(ML)／複数サービス連携。K-Bar AIは全部該当。
