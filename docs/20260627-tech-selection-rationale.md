# 技術選定の理由（K-Bar AI）

**日付:** 2026-06-27
**目的:** このアプリの各技術をなぜ採用したかを後から参照できるようにまとめる。

このアプリの本質は **「競馬データをスクレイピング → 機械学習で予想 → Webで可視化 → 個人運用、将来は外部公開」** という個人開発のMLプロダクト。この性格がほぼすべての技術選定を決めている。

---

## 1. Docker / docker-compose
**理由: 環境差をゼロにして「自宅Windows PC ⇄ 本番VPS(Linux)」を同じ構成で動かすため。**
- 自宅Windows PCで開発・JRA-VANスクレイピング（32bit環境必須）、本番VPS(Linux)でAPI・予想バッチ稼働。OSが違うのにPostgreSQL・Pythonランタイム・依存ライブラリを完全に同じバージョンで揃えたい。
- `docker-compose.yml`(開発)と`docker-compose.prod.yml`(本番)で構成を分離しつつベースは共通。
- LightGBMが`libgomp1`に依存するなどLinux固有の罠もDockerfileに書けば本番で再現できる。
- GitHub Actions → VPSで `git pull` + `build --no-cache` + `up -d` の自動デプロイが1コマンドで完結。
- 個人開発で環境構築に時間を溶かさない＝コスト削減方針と合致。

## 2. Python（バックエンド言語）
**理由: 機械学習が中核だから実質選択の余地がない。**
- LightGBM・scikit-learn・SHAP・pandas はすべてPythonエコシステムが事実上の標準。
- スクレイピング(Playwright)もPythonで完結。
- 予想モデル・Web API・スクレイパーを1言語で書けば、特徴量定義などのロジックを共有できる。
- GoやNode.jsだとML部分だけPython別プロセスになり個人開発には複雑すぎる。

## 3. FastAPI（Webフレームワーク）
**理由: Python製でMLと同居でき、async対応で軽く、型安全。**
- 同じPythonなので学習済みモデル(.joblib)をAPIプロセス内で直接読んで予測を返せる。
- async対応 — netkeibaライブオッズ取得など外部I/O待ちが多く非同期が効く(SQLAlchemy asyncと組合せ)。
- Pydanticの型・スキーマ自動検証 + OpenAPI自動生成でフロントとの契約が明確、バグが減る。
- Djangoは重すぎ、Flaskは非同期・型周りで一手間。「軽量×型安全×async」のバランスで最適。

## 4. PostgreSQL（データベース）
**理由: 競馬データは関係が複雑で大量、かつ高度なクエリが必要。**
- レース・馬・出走・オッズ・払戻と強い関係構造(NoSQL不向き)。学習データは161万件規模。
- ウィンドウ関数(過去5走の馬柱を1クエリ)などSQLの表現力が効く。
- postgres_fdw でアプリDB(kbar)からJRA-VAN DB(kbar_jravan)を別DB横断参照する高度な使い方をしている＝PostgreSQL固有の強み。
- MySQLでも可能だがFDW・ウィンドウ関数・JSON型の総合力で上。SQLiteは同時接続・規模で本番不可。

## 5. SQLAlchemy(async) + Alembic
**理由: 型安全なORMとマイグレーション自動化。**
- 生SQLより安全にPythonオブジェクトで扱える(asyncでFastAPIと整合)。
- Alembicでスキーマ変更をバージョン管理 → VPS起動時 `alembic upgrade head` で自動適用。新テーブル追加が本番に安全に反映。

## 6. LightGBM（機械学習モデル）
**理由: 表形式データの予測で最強クラス、かつ軽い。**
- 競馬データは表形式。この領域は勾配ブースティング木がディープラーニングより精度・速度で勝つのが定説。
- 学習が高速・省メモリで個人PC/VPSでも回せる。欠損値をそのまま扱える(競馬データは欠損多い)。
- カテゴリ変数対応、ランキング学習(LambdaRank)も可能。
- ※精度は構造的に頭打ち(市場オッズと同じ情報では市場を超えられない)と検証済だが、これはモデル選定でなくデータ(情報量)の限界。詳細=docs/20260613-model-improvement-findings.md

## 7. SHAP（説明可能性）
**理由: 「なぜこの馬を推すのか」を日本語で説明するため。**
- 予想AIはブラックボックスだと信用されない。将来の外部公開を見据えると「説明」が商品価値。
- 各特徴量の予測寄与を定量化し日本語ラベルに変換してユーザーに見せている。

## 8. Playwright（スクレイピング）
**理由: netkeiba/JRA公式の動的JS描画ページに対応するため。**
- オッズや馬場情報(含水率・クッション値)はJSで後から注入される → 静的curl/requestsでは空になる。
- 実ブラウザを動かしJS描画後のDOMを取得できる。
- 方針として間隔3〜10秒ランダムでアクセスし相手サーバーに配慮。

## 9. Next.js 15 + React 19（フロントエンド）
**理由: モダンなWeb UIを最小コストで、SEO/公開にも耐える形で。**
- 予想結果・オッズ・買い目提案などインタラクティブなUIが多い → Reactのコンポーネント志向が合う。
- 将来の外部公開時にSSR/ルーティング/最適化が標準装備で別途設定不要。
- エコシステムが巨大で情報が豊富＝詰まりにくくコスト削減。

## 10. Tailwind CSS 4
**理由: CSSファイルを別管理せず高速にUIを作るため。**
- クラスをHTMLに直接書く方式で「CSS設計」に悩む時間を削減。
- デザイナーがいなくても一貫した見た目を素早く作れる。
- 画面が多い(馬券シミュレーター・ヘッジパネル等)ので開発速度が効く。

---

## 全体を貫く選定思想
| 観点 | 効いている選択 |
|------|----------------|
| MLが中核 | Python / FastAPI / LightGBM / SHAP |
| 環境差をなくす | Docker(自宅⇄VPS) |
| 個人開発・低コスト | 情報量豊富なメジャー技術(Next.js, Tailwind, FastAPI) |
| 将来の外部公開 | Next.js(SSR/SEO)・SHAP(説明責任)・Docker(スケール・自動デプロイ) |
| 複雑な競馬データ | PostgreSQL(FDW・ウィンドウ関数) + SQLAlchemy/Alembic |
| 動的サイト取得 | Playwright |

ひとことで言えば **「機械学習を中心に据えつつ、個人で低コストに運用でき、将来は外部公開にも耐える」** 要件を満たす組み合わせ。
