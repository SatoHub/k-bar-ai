## 2. これまでに解説済みの内容（要点メモ）

### 第1回：全体像と層構造
- バックエンド＝「リクエストに対しデータ取得・計算して返す裏方」。レストランの厨房に例えた。
- このアプリのBEの4大仕事:
  ① スクレイピング `app/scraper/` ② AI予想 `app/ml/`
  ③ API応答 `app/api/` ④ 自動実行 `app/scheduler/`
- データの1日サイクル: 朝6:30スケジューラ→netkeiba収集→DB保存→AI予想→DB保存→
  昼ユーザー閲覧→API応答→画面表示。
- **層構造（最重要）**:
  - `api/`（受付係）→ `services/`（料理人＝本処理）→ `models/`（DB棚の設計図）
    ↔ PostgreSQL、返答は `schemas/`（書式チェック）で整形。
  - 技術スタック: FastAPI / SQLAlchemy(ORM) / PostgreSQL / LightGBM /
    Playwright / APScheduler / Alembic / uv。
  - `app/main.py`（玄関・52行）= FastAPIアプリ生成＋CORS＋スケジューラ起動＋router登録。

### 第2回：1本のリクエストを最後まで追う（題材 `GET /races?date=...`）
追ったファイル: `app/api/v1/races.py` → `app/database.py` →
`app/services/race_service.py` → `app/models/race.py` →（返答）`schemas`。

**設計を説明できるポイント①〜⑤（面接ネタ。本人が言えるようにするのがゴール）:**
1. **薄いコントローラ（Thin Controller）**: api層は「入力チェック・service呼び出し・
   返答整形」だけ。ロジックはservice層に隔離→API/スケジューラ両方から再利用＆テスト容易。
2. **DI（依存性注入）と async**: `Depends(get_session)`でDB接続を自動注入。
   I/O待ち支配的なのでasync/awaitで待ち時間に別処理→スレッド増やさずスループット確保。
3. **クエリ設計**: 一覧は全件返さず**ページネーション**（COUNTクエリ分離＋LIMIT/OFFSET）。
   発展: OFFSETは深いページで遅い→カーソルページネーションの余地。
4. **インデックス＆正規化（Phase0核心）**: `race_date` に index、`ix_races_date_course`
   複合index＝頻出の日付/競馬場検索を全件スキャン回避。indexは検索高速化と引き換えに
   書き込みコスト増のトレードオフ。テーブル分割(races/race_entries/horses)＝正規化で重複排除。
5. **N+1問題**: 関連データを1件ずつ取ると 1+N+N… クエリ爆発。詳細取得は `selectinload`
   でeager load、馬柱は ROW_NUMBER ウィンドウ関数で1クエリ化（`get_past_performances`）。
