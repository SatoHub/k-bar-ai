# K-Bar AI 総括 — 競馬AI予想アプリを作って、賭けでは勝てないと確定させた記録

作成: 2026-09-27（プロジェクト区切り時点）

> **結論から**: アプリは動いた。モデルも動いた。**だが「賭けて勝てる」見込みは無いと確定した。**
> 価値が残るのは **作ったもの** ではなく **作る過程で身についた検証の作法** と **基盤**。
> この文書はそれを次に持っていくために書く。

## 1. 何を作ったか

### 技術スタック（すべて実際に本番稼働した）

### 規模と稼働実績（実測）

- **学習データ 161万件**（1986-01-05 〜 2021-07-31 のレース結果）
- 本番稼働: 2026-02 〜 2026-09（**約7ヶ月**）。この間 **予想 29,072件**を自動生成し LINE 配信
- **締切前オッズ 510,108行 / 2,123レース**（2026-02-22〜09-27。**1レースあたり18スナップショット**）

- テスト 182件 / ruff clean / hook による自動チェック（Python は ruff+対応テスト、TS は tsc）

**「作ったが動かなかった」ではない。** 毎朝スクレイピングし、予想を生成し、LINE に飛ばし、
結果を集計し、証明書を自動更新し、7ヶ月間落ちずに（1回の 502 を除いて）動き続けた。

## 2. 何を試して、何が分かったか

### モデルの性能（すべて out-of-sample 実測）

| 指標 | 値 |
|---|---|
| ROC-AUC（3着内予測・v1.0.0〜v1.2.0） | **0.811** |
| accuracy / F1 | 0.812 / 0.429 |
| **オッズ関連2特徴量をシャッフルした時の AUC** | **0.8115 → 0.5068** |

🔴 **これが全てを説明する。0.5068 はほぼコイン投げ。**
**単勝オッズを取り除くとモデルは予測能力をほぼ完全に失う。**
`win_odds` 単独の寄与が +0.245 で、**残り40特徴量の合計が +0.008 未満**。
つまり **AUC 0.81 はモデルの実力ではなく市場（みんなの賭け方）の精度を映していた。**

### 3つの角度から「勝てない」を確認した

| 検証 | 結果 |
|---|---|
| **① モデル単体で妙味馬を拾う**（`p_model > p_market`） | **50,398点 ROI 72.7% CI[66.5, 79.2]** → CI上限が100%未満＝**有意に赤字**（判定不能ではない） |
| **② Benter流の二段モデル**（重みをデータから学習） | **α = −0.0580 / SE 0.0322 / p = 0.0714 / CI[−0.121, +0.005]** → **市場に情報を足せていることを示せなかった**。尤度比検定も p=0.0717 で一致 |
| ③ 特徴量バグ（24個）を直して再学習 | **AUC 0.81149。修正前と小数第4位まで同一。天井は動かなかった** |

③について: 「v1.1.0 で改善しなかったのは追加した6特徴量が壊れていたせいだ」という
仮説を立てて24個のバグを直したが、**数字は 1桁も動かなかった＝仮説は否定された**。
真の理由は上のオッズ支配で、バグ修正は正しかったが天井を破る鍵ではなかった。

②の補足: 「棄却できない」は「ゼロである」の証明ではない。言えるのは**効果量の上限**で、
情報を足す方向の上限は **+0.005 = 市場の係数 β=0.892 の 0.6%**。
out-of-sample の対数損失改善は **+0.00105（0.05%）** で実質ゼロ。
なお `logit(p_model)` と `logit(p_market)` の相関は **0.824** で多重共線性はあるが、
α の SE は 0.032 と小さく検出力不足では説明しきれない。

### 市場の効率性を実測した（副産物だが価値がある）

| 実測値 | 意味 |
|---|---|
| `Σ(1/オッズ)` のレース平均 = **1.2529** | 控除率 **20.18%**（JRA公式の単勝20%と一致）→ DBのオッズが確定オッズである証明 |
| 全馬均等買いの ROI = **75.2%** | 控除率から期待される 79.8% より**低い** → **人気薄が過剰に買われている**（favourite-longshot bias）。穴狙いは出発点で 4.6pp 不利 |
| 1番人気の単勝 ROI = **79.8%**（5,585点） | 理論値 1/1.2529 = 79.8% と小数第1位まで一致 |
| 条件付きロジットの β = **0.892**（CI [0.844, 0.940]） | 1 を含まない＝市場のロジットはわずかに縮める方が当たる。上記バイアスの別の現れ方 |

### 🔴 結論

> **現在のデータ（netkeiba の公開情報 + 確定オッズ）で作れるモデルに、
> 賭けて勝てる見込みは無い。**
> モデルは実質「単勝オッズの言い換え」であり、問いの立て方を変えても
> （単体 vs 市場 / 市場に足せるか）結果は変わらなかった。

⚠️ 限界も併記する。**確定オッズで採点しているので、測定値は現実より楽観的**である。
複勝以降の券種は払戻オッズを保持していないため**評価していない**（未確認）。

## 3. 見つかった不具合と、なぜ気づけなかったか

**ここがこの文書の一番の資産。** すべて「動いているように見えて壊れていた」もの。

### ① 集計特徴量24個が別の馬・別の騎手の値を拾っていた

```python
finish_shifted = grouped["finish_position"].shift(1)      # ← groupby 内で正しい
df["horse_avg_finish_3"] = finish_shifted.rolling(3).mean()  # ★ groupby の外
```

`grouped[col].shift(1)` は**素の Series** を返す。そこに `.rolling()` を直接かけると
窓がグループ境界をまたぐ。**12個は `expanding` で全行汚染**（騎手の通算勝率が
「データ全体の累積平均」になっており騎手固有の情報をほぼ持っていなかった。
`cumulative_prize` は実質「行番号」）。残り12個は各グループ先頭が汚染。
しかも `expanding` は並び順の先頭から累積するため **2020年以降のレースが
2019年以前の学習行に混入**していた（未来情報リーク）。

**なぜ気づけなかったか**: リーク検査のテストは**既にあった**。しかし全て `n_horses=1`
（単一の馬・騎手）で書かれていた。**バグは「別のエンティティの値を拾う」ものなので、
エンティティが1つしかないテストでは構造的に検出できない。**
2頭使っていたテストは列の存在だけを見て値を検証していなかった。
そして `"All rolling features use shift(1) to prevent future data leakage"` という
**コメントを検証の代わりにしていた**。

### ② post-edit hook の結果が Claude に届いていなかった

自動チェックは走っていたが、失敗結果が `systemMessage` にしか出ておらず
**Claude には渡っていなかった**。人間には出力が見えるので「動いている」ように見えた。

### ③ guard hook の fail-open 3経路と、正規表現1つでループ全体が脱出

危険操作をブロックする hook が、①`Bash` だけを見て `PowerShell` を素通り
②正規表現1つが壊れると例外でループを抜けて**全ルートが無効化**
③ヒアドキュメント内を検査していない。**変更規模は設定ファイル1つ＝Medium だったが、
中身は全ての防御を無効化する穴だった。危険さと差分の大きさは相関しない。**

### ④ `deploy.sh` のヘルスチェックが 3xx を成功扱い

HTTPS化で 80番が 302 を返すようになった後、`curl -sf` は 3xx を成功と見なすため
**アップストリームが死んでいても「正常」と報告する**状態だった。

### ⑤ systemd の `OnFailure` を `[Service]` に書いて黙って無効化

`OnFailure=` は `[Unit]` セクションのディレクティブ。`[Service]` に書くと
**systemd はエラーを出さず単に無視する**。失敗通知が飛ばない状態で「設定済み」だった。

### ⑥ `.htpasswd` を 640 にして worker が読めず、しかも露見しない

nginx の worker は非 root で動くので読めない。**未認証アクセスには 401 を返すので
一見正常**で、正しいパスワードを入れた人だけが 500 を食らう。

### ⑦ nginx の `upstream` が起動時に1度しか名前解決しない

`upstream { server backend:8000; }` は設定読み込み時に1度だけ解決して IP を保持する
（`server ... resolve;` は nginx Plus 限定）。自動デプロイは backend/frontend を
作り直すが nginx は再起動しない。**IP がちょうど入れ替わって、API が frontend に、
画面が backend に飛んで本番が全ページ 502 になった。**
IP が偶然同じ値で再割当されれば何も起きないので、**発覚するかどうかは運任せ**だった。

### ⑧ ROI 集計が未確定レースを「賭けてハズレ」として数えていた

オッズは結果より先に入るため、822件が「賭けたが外れた」扱いになり ROI が過小に出ていた。
的中率も同じ欠陥を持っていた。

### ⑨ 損益分岐点を控除率と取り違えた

ROI の損益分岐は **1.00**。控除率 0.80 は「無策で賭けた時の期待値」であって分岐点ではない。
`breakeven_roi_vs_takeout = 0.80` と命名したため **ROI 0.85 を「賭ける価値がある」と
読ませる導線**になっていた。レビュー3件が独立に指摘した。

### ⑩ 診断コードが学習成果を消していた

追加したサニティチェックが categorical 列の dtype を壊し、LightGBM が例外を投げる。
しかも artifact 保存の**前**なので、**数十分かけた学習が .joblib にも DB にも残らず消える**。
別モデル（Codex）が P1 として検出した。

### ⑪ 🔴「修正した」と書いた箇所が実際には修正されていなかった（複数回）

- `calibration` の異常系: 「異常系が『問題なし』として通過する欠陥を修正した」と
  コミットに書いたが、**定数を吐くモデルは ECE=0.0 / OK で通過していた**。
  KeyError を消しただけで意味論は未修正だった
- 予測時の特徴量列: artifact に保存した列ではなく現在の列定義を使っていた。
  LightGBM は列名を検証せず並べ替えもしない（**列順を変えると予測値が最大 0.869 変わる**）
- 主判定の定義: `p_blend − p_market` にしていたが、α̂≈0 でも β̂≠1 なら差が出るため
  **α の寄与を測っていなかった**
- 自分が追加したテストが無検査だった: `pytest.approx` の既定の絶対許容 1e-12 が
  p≈1e-133 を無条件に一致させ、**p値を片側化しても通っていた**

**共通する原因: 自分のコミットメッセージや関数名を、検証の代わりにしていた。**

### ⑫ 🔴 本番の予測が、学習時と全く違う特徴量の上で7ヶ月間動いていた（train/serve skew）

最終日の調査で発覚。**本番DBには 2026-02-22 より前のデータが 0件**しか無い。
一方モデルは 1986〜2021 の35年分の履歴から計算した特徴量で学習されている。
本番で予測時に使える「その馬の過去走数」を実測すると:

| 過去走数 | 出走行 | 割合 |
|---|---|---|
| **0走（rolling特徴量が全て NaN）** | 9,434 | **32.5%** |
| 1〜2走 | 12,785 | 44.1% |
| 3〜4走 | 5,285 | 18.2% |
| 5走以上 | 1,505 | **5.2%** |

`horse_avg_finish_5` や `horse_win_rate_5` が成立するのは **全体の 5.2% だけ**。

**なぜ気づけなかったか**: モデルは `win_odds` に支配されており（シャッフルで
AUC 0.8115 → 0.5068）、**オッズは本番でも新鮮に取れている**。だから近走成績が
空っぽでも予想は「人気順に近い妥当な並び」に見え、出力が破綻しなかった。

**この発見は今日の結論を強める。** 「本番のモデルは実質オッズのランキングだった」ことが、
オフライン評価とは**独立に**裏付けられた。

### ⑬ JV-Link の日次同期が 106回連続で失敗していたのに誰も気づかなかった

自宅PCの Windows タスクは今も毎朝動いているが、**2026-06-11 20:30 を最後に成功していない**
（6月19回 / 7月31回 / 8月29回 / 9月27回の失敗）。原因は朝6:30に Docker(PostgreSQL) が
起動していないこと（**推測**。エラーは DB 接続失敗で一致するが実行時刻の Docker 状態は未実測）。

**なぜ気づけなかったか**: JRA-VAN は本番の予想経路に使われていない（本番 race_entries
29,009件すべて `data_source='scrape'`）。**止まっても外から見て何も壊れないので、
失敗が表に出なかった。** バッチの成否を通知していなかったのが直接の原因。

### ⑭ その他

- 検証用分割が `iloc[:90%]` の位置ベースで、df がエンティティ順だったため
  コメントの「時系列の後ろ10%」とは違う集合（＝特定の馬の集まり）になっていた
- `nginx -s reload` は**非同期**。古い worker がメモリ上の旧証明書を配り続けるため、
  reload 直後に読むと「変わっていない」と誤判定する（実測: 6秒後もまだ旧証明書）
- Windows の git は実行ビットを記録しないので systemd の `ExecStart` が `203/EXEC` になる
- `.gitattributes eol=lf` は git 経由のチェックアウトしか守らない（tar 転送で CRLF が混入）
- 自分が書いたテストが seed 依存の flaky だった（10個の独立な95%CIを1回で見ており、
  実装が正しくても約40%で落ちる。seed 31/41 で実測）

## 4. 方法論として学んだこと

### ① 判定基準を測定前に決めて commit する

同日、113レースで1番人気の ROI を測って **106.6%** という数字が出た。
控除率20%の単勝で長期 106.6% はあり得ないのに、一瞬「市場が AI に勝っている」と読みかけた。
5,585レースで測り直したら **79.8%**（理論値と一致）。**完全なノイズだった。**

そこで**測る前に**基準を文書化して commit した。その効果:

```
2025年 edge>0    341点  ROI 133.8%  CI[37.3, 266.8]  必要45,877点  → 判定不能
```

**ROI 133.8% を「判定不能」と切れた。** 基準が後出しなら「有望」と読んでいた。
**測ってから基準を作ると、出た数字に合わせて基準が動く。**

### ② サンプルサイズの構造的な壁（これは競馬に限らない）

単勝1点の収支 `X = オッズ × 当たり` の標準偏差を実測すると:

| オッズ帯 | sd(X) | CI半幅0.10に必要な点数 |
|---|---|---|
| 1〜3倍 | 1.08 | **446** |
| 6〜12倍 | 2.45 | 2,301 |
| 30倍以上 | **8.66** | **28,803** |

**必要点数が 65倍違う。** 「何点あれば信じていいか」は一律には決められない。
**人気薄を買う戦略は、手元の全データ（5,585レース）を使っても構造的に判定不能。**
「穴で高ROIが出た」はほぼ必ずノイズ。
→ 点数を固定せず **精度要件（CI半幅 ≤ 0.10）＋ 絶対下限（N ≥ 500）** で決める設計にした。

### ③ テストが機能するかを mutation testing で確認する

「テストがある」ではなく「**テストが落ちる**」を確認する。実際に:
- 判定順序の入替え / ECE の重み付け除去 / bootstrap を50%区間に / degenerate 無視
  → 4種すべて入れ直して落ちることを確認
- **p値の片側化（SE過小と同じ症状）は27件全部素通りしていた**。
  原因は偽陽性率テストの検出力不足（真の偽陽性率が2倍に悪化しても検出確率4.3%）
  → z の分布そのものを KS 検定する方式に置き換えた

**「確率的な検定のテスト」は検出力を計算してから書くこと。** 感覚で反復回数を決めると
「安定して通るが何も検出しない」テストになる。

### ④ コメントの安全性主張を検証の代わりにしない

- `"All rolling features use shift(1) to prevent future data leakage"` → 実際は壊れていた
- nginx の「本文サイズと**流量**を絞る」→ `limit_req` は**1件も存在しなかった**
- 自分のコミットメッセージ「異常系を修正した」→ 実際は通過していた

**防御していると書いてあるのが一番危険。** レビュー時に「対策済み」と誤認させる。

### ⑤ レビューを複数回すことには実効性がある（気分ではなく実績で）

| レビュアー | 実際に見つけたもの |
|---|---|
| **別モデル（Codex）** | サニティが学習成果を消す P1 / guard hook が PowerShell を素通り / 非完走馬の除外バイアス / 「棄却できない」を「無い」と断定する推論の誤り |
| `code-reviewer` | 予測時に artifact の特徴量列を使っていない（列順違いで予測が最大0.869変わる実測付き）/ **主判定が α の寄与を測っていない** |
| `security-reviewer` | 定数を吐くモデルが calibration_ok=True で通過（実測）/ 実在しない流量制限のコメント |
| `test-reviewer` | mutation testing で**テストの穴を定量的に実証**（検出確率4.3%まで計算） |

**同じモデルのレビュアー同士は同じ勘違いをする。** 認証・並行処理・統計が絡む変更で
別モデルを省略しない理由がこれ。一方 **レビューを鵜呑みにもしない**:
「bootstrap CI の退化で精度チェックを素通り」という指摘は 75通り探して0件で、
**コードではなくテストの前提が誤っていた**ので、テスト側を直した。

### ⑥ 「示せなかった」と「無いと示された」を書き分ける

帰無仮説を棄却できないことは帰無仮説の証明ではない。
事前に等価性マージンを登録していないなら、言えるのは**効果量の上限**だけ。
これを混同すると「調べ尽くした」と誤認して撤退判断を誤る。

## 5. 正直な自己評価

### うまくいった

- **インフラは筋が通っている。** ドメイン無しの環境で Let's Encrypt の IPアドレス証明書
  （160時間有効）を自動更新する仕組みを作り、**実際に2回の自動更新を誤報ゼロで通した**。
  失敗時は LINE に 🔴 が飛ぶ多段通知付き
- **7ヶ月間動き続けた。** 落ちたのは最後の 502（nginx の IP キャッシュ）1回だけ
- **やめる判断を、数字で出せた。** 「なんとなく勝てない気がする」ではなく
  ROI の信頼区間と係数の p 値で確定させた。**これが一番の成果**
- 検証の作法（事前登録・mutation testing・多段レビュー）が身についた

### やり直すならこうする

- 🔴 **最初に「オッズを外したらどうなるか」を測る。** これを7ヶ月やらなかった。
  1日でできたはずで、やっていればモデル改良に費やした時間の大半は不要だった。
  **「精度が出た」で満足せず、何がその精度を作っているかを分解する**
- 🔴 **賭けの検証は ROI から始める。** AUC を追いかけたが、AUC 0.81 と ROI 72% は両立する。
  目的変数が「儲かるか」なら、最初から ROI と信頼区間で見るべきだった
- **合成データでの検証を先に書く。** 24特徴量のバグは、2頭の合成データで期待値と
  突き合わせれば初日に見つかった。「関数が呼べる」テストを量産していた
- **データ取得の設計を先に決める。** `odds_snapshots`（締切前オッズ）を溜め始めたのが
  2026-02。もっと早ければ「市場が何を知らないか」を測る土台があった
- **スコープを広げすぎた。** 買い目提案・ヘッジ・穴馬検出・シミュレーター・血統表示…
  中核（勝てるか）が未確定のまま周辺機能を増やした
- **JRA-VAN の契約タイミングが早すぎた。** 何に使うかを決める前に契約した

### 誤魔化さずに書くこと

- 途中「特徴量を足せば良くなる」と何度も期待し、そのたびに改善ゼロだった。
  **v1.1.0 で改善しなかったのは追加特徴量が壊れていたせいだ**という仮説も立てたが、
  直しても数字は小数第4位まで同じで、**仮説は否定された**
- **本番に v1.0.0 を置いたまま、より良いモデルを作れなかった。** v1.1.0 / v1.2.0 は
  どちらも本番採用の理由が無い

## 7. JRA-VAN 解約後、このプロジェクトをどうするか（未決定・選択肢）

### JRA-VAN の使用実態（コードから確認した事実）

- **JVLink は自宅 Windows PC 専用**（32bit venv `backend/jravan/.venv32`）。
  別DB `kbar_jravan` に投入し、Windows タスクで毎朝6:30に差分同期
- 本番 VPS には FDW を張っておらず、**自己完結テーブルを pg_dump で同期**する方式
  （`horse_pedigree` 2,729件 / `confirmed_win_odds` 3,479件 / `confirmed_payouts`）
- **予想生成には使っていない。** 予想は netkeiba スクレイピング由来のデータで動く

→ **解約しても本番は止まらない。** 止まるのは血統表示（カバレッジ25%）と
確定オッズ・払戻の補強データの**更新**だけ。既存データは DB に残る。

### ⚠️ 遡って取れるもの / 取れないもの（判断の分かれ目）

| データ | 遡及取得 |
|---|---|
| レース結果・馬・騎手などの通常データ | **可能**（JV-Data は過去アーカイブを持つ） |
| **公式時系列オッズ（単複枠・馬連 `TS_O1`/`TS_O2`）** | **約1年分のみ**（JRA-VAN 側の保持期間）。再契約時点から1年しか遡れない |
| 速報系の全賭式オッズ（`TS_SOKUHO_O1〜6`） | **約1週間のみ** |
| `corner_pos_1..4`（通過順） | 結果に付随するので取得可能。現状 `corner_pos_4` は 99.3% 充填、`corner_pos_1` は 42.8% |
| **自前の `odds_snapshots`**（netkeiba 由来・JRA-VAN とは無関係） | **原理的に不可**。リアルタイムでしか取れない |

🔴 **重要な訂正**: 締切前オッズは「直近レースのみ」だと思っていたが、**本番には
2026-02-22〜09-27 の 2,123レース・510,108行が蓄積されていた**（1レースあたり18スナップショット）。
**これは JRA-VAN とは無関係に、本番スケジューラが自力で溜めたもの。**
つまり「市場が締切前にどう動いたか」の7ヶ月分の資産は**解約しても失われない**。
ただし**本番を止めると、そこから先は永久に埋まらない。**

### 選択肢（ユーザー判断待ち）

| 案 | 内容 | 得るもの / 失うもの |
|---|---|---|
| **A: 本番を止める** | VPS のコンテナを停止。DB は pg_dump でバックアップして保管 | VPS 費用と保守がゼロになる。**`odds_snapshots` の蓄積が止まる**（再開しても穴が空く） |
| **B: 動かし続ける（データ収集のみ）** | 予想生成・LINE通知は止め、**スクレイピングと `odds_snapshots` だけ残す** | 月数百円〜のVPS費用で「市場の動き」の蓄積を継続。将来の再挑戦の土台が残る。保守は証明書自動更新があるのでほぼ不要 |
| **C: そのまま動かし続ける** | 現状維持。予想も通知も続ける | 娯楽・ポートフォリオの実演として残る。**勝つ目的では意味が無いと分かっている点は自覚しておく** |
| **D: 縮小して別VPSへ相乗り** | 既に shitagoshirae と同居しているので構成変更のみ | コストは変わらない（同一VPS）。整理の手間だけ |

**判断材料の要点**: 失って戻せないのは **`odds_snapshots` の継続性**だけ。
モデルも予想もいつでも作り直せる。**「将来データを増やして再挑戦する道を残す」なら B が最小コスト。**
その道に興味が無いなら A で良い（DB をバックアップしておけば7ヶ月分は残る）。
